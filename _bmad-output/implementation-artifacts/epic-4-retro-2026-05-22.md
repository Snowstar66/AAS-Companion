# Epic 4 Retrospective: Uploaded Snapshot UX and Adapter

Date: 2026-05-22
Project: AAS-Companion
Epic: Uploaded Snapshot UX and Adapter
Status: completed

## Executive Summary

Epic 4 gjorde den säkra uploaded snapshot-grunden från Epic 3 användbar i Control Mirror. Flödet är nu synligt, explicit och policybundet: användaren väljer filer själv, ser begränsningar före submission, får resultat efter ingestion och får fail-closed felmeddelanden när inget snapshot skapades.

Det viktigaste utfallet är att Control Mirror nu kan ta emot användarvalda projektfiler utan att antyda lokal folder scanning, repository scanning eller implicit åtkomst. Samtidigt bevaras de centrala kontrollprinciperna: backendvalidering, retention/redaction, deterministisk refresh via normaliserad path/hash och kompatibilitet med Human Review-reconciliation.

Den tydligaste nästa risken är att Control Mirror-logiken fortsatt växer i samma domän- och sidytor. Epic 4 lyckades hålla upload-specifik adapterlogik avskild, men dashboard, policy, conformance, report och review-identity delar fortfarande många beröringspunkter.

## What Worked

- The Epic 3 "policy before capability" lesson carried through. Uploaded snapshot became actionable only after the UI could state limits, retention posture and no-silent-scan behavior clearly.
- Splitting the browser/server payload conversion into `uploaded-snapshot-adapter.ts` kept transport concerns away from the domain ingestion rules.
- Reusing `createControlMirrorUploadedSnapshot()` avoided duplicate validation logic and preserved backend authority for accepted, rejected and unreadable files.
- URL state for `?source=uploaded-snapshot` gave the page a simple way to preserve upload panel state across preparation, success and failure.
- Result summary work made ingestion outcomes observable: accepted, rejected, unreadable, unchanged, new, modified and deleted counts are now visible together.
- Story 4.4 added the right kind of regression coverage: repeated identical uploads remain unchanged, and Human Review keys stay stable across uploaded snapshot refreshes.

## What Was Hard

- Control Mirror changes are still cross-layer by nature: domain read model, repository JSON mapping, API service, server action, App Router page and Vitest coverage often move together.
- File upload tests require careful fakes because runtime `File` support in Vitest is not identical to browser/server behavior.
- The page now carries more operational state: source mode, upload form, upload result summary, retention disclosure and error messaging.
- Fail-closed copy matters more than it first appears. A generic error can accidentally imply a scan may have succeeded, so failure language had to be explicit.
- Review identity is sensitive to small modeling choices. Refresh counts and snapshot IDs must not leak into stable finding keys when the underlying finding is the same.

## Key Lessons

1. Uploaded evidence must stay user-explicit from first click to persisted result. The product copy, action wiring and server behavior all need to say the same thing.
2. Adapter boundaries are worth keeping even for small upload flows. They make file limits, unreadable handling and metadata preservation testable without bloating the page.
3. Ingestion result summaries are not just UX polish. They are part of the trust contract because they show what was accepted, rejected, unreadable or unchanged.
4. Fail-closed error states need direct language. "No snapshot was created" is operationally clearer than a generic submission failure.
5. Human Review reconciliation depends on stable artifact/finding identity, not on latest snapshot IDs or transient refresh labels.

## Quality And Readiness Assessment

Testing and quality: Green for targeted Control Mirror coverage and production build.

Deployment readiness: Code builds successfully. No new schema tables were required for Epic 4.

Stakeholder acceptance: Not formally recorded. Product/security review should still confirm the file limit wording, retention/redaction disclosure and fail-closed error copy before treating the workflow as release-ready for broad users.

Technical health: Stable, with increasing modularization pressure. The upload adapter is a good local boundary, but `packages/domain/src/control-mirror.ts`, the Control Mirror page and repository summary mapping remain high-traffic surfaces.

Known residual risks:

- Archive/zip extraction is still not implemented; the current workflow handles selected files rather than compressed project snapshots.
- Folder snapshot and Git/repository root remain planned/unsupported and non-actionable.
- Redaction catches known patterns but is not a complete security scanner.
- Retention and upload summary metadata still rely on JSON shapes that may deserve typed schema support later.
- Formal product/security acceptance is not captured in sprint artifacts.
- Existing build/test warnings remain non-blocking but noisy.

## Next Epic Preparation

No Epic 5 is currently defined in sprint tracking.

Recommended next paths:

1. Control Mirror Modularization: split source policy, upload summary, conformance, review reconciliation and report composition into smaller domain modules.
2. Report and Evidence Pack Export: make Control Mirror output durable and exportable with retention/redaction disclosure.
3. Uploaded Archive Intake: add deterministic archive extraction only if product/security accepts the expanded evidence boundary.
4. Human Review Workspace Integration: surface Control Mirror review queue and decision history more directly in `/review`.

Recommended starting point: define Epic 5 as **Control Mirror Modularization** if the goal is to reduce implementation risk before the next capability family, or **Report and Evidence Pack Export** if the goal is to make current Control Mirror results easier to share and audit.

## Retrospective Outcome

Epic 4 is complete from story, test and build perspectives. The uploaded snapshot workflow is usable enough for controlled validation, provided the next planning slice either hardens the architecture around Control Mirror or turns the completed results into durable report/export artifacts.
