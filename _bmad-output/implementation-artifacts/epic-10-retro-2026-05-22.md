# Epic 10 Retrospective: Export Acceptance Workflow Hardening

Date: 2026-05-22
Project: AAS-Companion
Epic: Export Acceptance Workflow Hardening
Status: completed

## Sammanfattning

Epic 10 gjorde acceptance-flödet mer robust. Exporthistoriken räknar nu readiness över alla required reviewer roles, server action stoppar reviewer-role submissions som inte matchar aktiv medlemsroll, och acceptance events kan återkallas med `revoked` utan att skriva om historik.

Det viktigaste resultatet är att en enskild acceptance decision inte längre kan misstolkas som full delningsklarhet. Exporten blir `Share ready` först när Product owner, Security/privacy och AQA har senaste beslut som accepterar rollen.

## Slutförda Stories

- Story 10.1: Compute Multi-Role Acceptance Readiness
- Story 10.2: Gate Reviewer Role Submission by Active User Role
- Story 10.3: Add Supersede and Revoke Acceptance Events
- Story 10.4: Harden Acceptance Workflow Regression and Retro

## Vad Som Fungerade

- Readiness kunde byggas från befintlig eventhistorik utan ny tabell eller payload rewrite.
- Latest-event-per-role gav en enkel supersede-modell: nya beslut ersätter äldre beslut för readiness men bevarar alla events.
- Role gate gick att lägga i server action före API-persistens, vilket gav tydligt fail-closed-beteende.
- `revoked` som eventtyp löste revoke utan delete/edit-semantik.
- Testerna fångar både dataregeln och action-gränsen utan att behöva full end-to-end browserkörning.

## Vad Som Var Svårt

- Aktiv session har medlemsroll, inte full Party Role Directory authority. Security/privacy fick därför mappas pragmatiskt till `architect` eller `aida`.
- Download-recordtypen återanvände export-recordtypen, så acceptance summary behövde få default även där för typkonsistens.
- Enum-ändringen kräver både Prisma generate och runtime package build innan web-testerna ser den nya typen.

## Lärdomar

1. Acceptance readiness ska beräknas från senaste event per roll, inte från senaste event totalt.
2. Revoke är säkrare som event än som mutation; audit-spåret förblir intakt.
3. Server actions är rätt första gräns för role gating, men Party Role Directory bör bli nästa auktoritativa källa.
4. UI-copy bör skilja pending, changes requested och share ready, eftersom de leder till olika governance-beslut.
5. Schema-enumändringar ska alltid följas av `db:generate`, package build och riktad web-regression.

## Readiness Assessment

Testing and quality: Grönt för multi-role readiness, role-gated acceptance submissions, revoke/supersede semantics, Control Mirror page readiness display och route stability.

Deployment readiness: Kräver DB-migrationerna från Epic 8, 9 och 10 i målmiljö:

- `20260522103500_control_mirror_evidence_pack_exports`
- `20260522111500_control_mirror_export_acceptance_decisions`
- `20260522124500_control_mirror_acceptance_revoked_decision`

Technical health: Bättre än före Epic 10. Acceptance workflow är fortfarande event-baserat, tenant-scoped och testbart, med tydligare separation mellan generated, pending, blocked och share-ready exports.

Residual risk:

- Party Role Directory används inte ännu som auktoritativ reviewer assignment-källa.
- Security/privacy-mappningen är pragmatisk och bör produktbeslutas.
- UI visar fortfarande alla reviewer choices även om server action blockerar otillåtna submissions.
- Export retention/archive och re-download audit events saknas fortfarande.
- Befintliga React/Next/webpack-varningar skapar fortsatt brus.
