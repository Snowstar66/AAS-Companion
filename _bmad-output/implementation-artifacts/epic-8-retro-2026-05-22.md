# Epic 8 Retrospective: Persisted Export History

Date: 2026-05-22
Project: AAS-Companion
Epic: Persisted Export History
Status: completed

## Sammanfattning

Epic 8 gjorde Control Mirror evidence packs hållbara. Varje lyckad JSON- eller Markdown-export skapar nu en tenant-scoped historikpost, Control Mirror-sidan visar senaste exporter, och tidigare exporter kan laddas ner igen från den sparade posten.

Det viktigaste resultatet är att exporten nu fungerar som audit history, inte bara som en fil som genereras i stunden.

## Slutförda Stories

- Story 8.1: Add Evidence Pack Export History Persistence
- Story 8.2: List Recent Evidence Pack Exports
- Story 8.3: Re-download Persisted Evidence Pack Exports
- Story 8.4: Harden Export History Regression Coverage and Retro

## Vad Som Fungerade

- Epic 7:s stabila exportmodell gjorde persistence-slicen rak: samma evidence pack payload används för JSON, Markdown och sparad historik.
- Fail-closed route-kontraktet gick att bevara när exporten började persisteras.
- Metadata-listan kan renderas utan att läsa full payload, vilket håller UI-slicen lätt.
- Re-download-routen kunde använda sparat filename/content type, vilket skyddar artifact-identiteten.
- Samlad regression över payload, route, repository och page gav bra signal.

## Vad Som Var Svårt

- `@aas-companion/db` läses från byggd package-output i web-testerna, så nya DB-exporter kräver runtime package build innan test.
- `exactOptionalPropertyTypes` fångade återigen en optional-parameter som inte fick skickas som `undefined`.
- Testfixtures behövde växa när exporthistoriken blev verklig nog att stödja både listning och re-download.

## Lärdomar

1. Persisted audit artifacts behöver skapas i samma service som bygger exportens body, annars kan download och historik glida isär.
2. Listvyer ska ha egna metadata-selects och inte råka bära med full payload.
3. Re-download ska returnera sparat filename och content type, inte räkna om dem från dagens regler.
4. Schemaändringar i DB-paketet bör följas direkt av `db:generate` och package build innan web-tester.

## Readiness Assessment

Testing and quality: Grönt för persistence, create/list/get, route download, payload safety, Markdown och page disclosure.

Deployment readiness: Kräver databas-migrationen `20260522103500_control_mirror_evidence_pack_exports` innan production använder exporthistorik.

Technical health: Bättre än före Epic 8. Exporthistorik är separerad i repository/API/route/UI och payload-listning är metadata-only.

Residual risk:

- Ingen delete/archive-policy finns för gamla exporthistorikposter.
- Ingen explicit product/security signoff på retention-copy och exportfält finns ännu.
- Re-download saknar ännu separat audit event för själva re-download-händelsen.
- Befintliga test/build-varningar skapar fortsatt brus.

## Rekommenderad Nästa Väg

Det finns ingen Epic 9 i sprintstatus ännu.

Rekommenderade nästa alternativ:

1. Product/Security Acceptance: formalisera fälturval, retention-copy och delningsregler för sparade audit artifacts.
2. Export Retention Governance: archive/delete-policy, retention disclosure och administrativ kontroll för exporthistorik.
3. Re-download Audit Events: logga vem som laddar ner tidigare exporter.
4. Conformance Modularization: fortsätt bryta ut framing/build/AI-level conformance från dashboardmotorn.
5. Warning Cleanup: ta bort kända React/Next/webpack-varningar.

Rekommenderad startpunkt: **Product/Security Acceptance** om målet är release-readiness för governance. Välj **Export Retention Governance** om nästa prioritet är teknisk kontroll över sparad historik.
