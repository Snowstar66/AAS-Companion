# Epic 2 Retrospective: Control Mirror Human Review Workflow Hardening

Date: 2026-05-21
Project: AAS-Companion
Epic: Human Review Workflow Hardening
Status: completed

## Executive Summary

Epic 2 completed the shift that Epic 1 deliberately left open: Control Mirror Human Review is no longer only a generated recommendation surface. It now has a first-class persisted review queue, explicit human-owned decision events, lifecycle-aware dashboard/report behavior and reconciliation across snapshot refreshes.

The strongest outcome is auditability. AI-generated findings remain recommendations, while human decisions require actor and rationale, are stored as append-only events, and drive readiness/report state through persisted lifecycle data.

The main remaining product question is what Control Mirror should harden next: source ingestion, evidence parsing fidelity, report/export durability, or deeper integration into the broader `/review` workspace.

## What Worked

- Starting with the queue model before decisions kept the persistence foundation narrow and stable.
- The stable finding key became the central design lever. Once volatile affected-count text was removed, duplicate prevention and refresh reconciliation became much safer.
- Keeping decision events append-only made audit semantics clearer and avoided overloading the review item row with mutable approval meaning.
- Recalculating dashboard/report state after queue merge kept UI, report preview and readiness aligned from the same read model.
- Focused tests paid off: they caught aggregate-key volatility, helper naming collisions, brittle UI text assumptions, and the reappearance edge case for superseded findings.

## What Was Hard

- Control Mirror now crosses domain, DB, API, App Router and test layers. The vertical slice is useful, but every lifecycle change touches several layers.
- Exact optional TypeScript types were helpful but unforgiving when adding the review-state summary model.
- The relationship between generated findings and persisted queue state needed careful ordering. Generated findings create the current observed set; persisted rows supply identity, lifecycle and decision history.
- Snapshot refresh semantics have subtle edge cases. Missing findings should not be deleted, but reappearing superseded findings must become actionable again.
- Running tests while rebuilding runtime packages can create temporary dist resolution failures. The build/test workflow needs sequence discipline.

## Key Lessons

1. Human decision data should be modeled separately from AI recommendations, even when the UI presents them together.
2. Stable keys must avoid volatile aggregate text. Entity ids and finding/category identity are better anchors than user-facing counts.
3. Readiness/report calculations should happen after persisted lifecycle merge, not only in the original deterministic domain generation step.
4. Refresh reconciliation needs both disappearance and reappearance rules. Superseding alone is not enough.
5. Page tests should expect repeated operational labels when the UI intentionally shows both summary and detail views.

## Quality And Readiness Assessment

Testing and quality: Green for targeted Control Mirror coverage and production build.

Deployment readiness: Code builds successfully. Local DB schema was generated and pushed during schema-changing work.

Stakeholder acceptance: Not formally recorded. The workflow is ready for product/mandate review, especially around decision labels and what "approve", "exception" and "downgrade" should imply operationally.

Technical health: Stable, but Control Mirror now has enough domain mass that further conformance expansion should consider extraction into smaller modules.

Known residual risks:

- Decision history is persisted, but the UI currently shows latest decision rather than a full chronological history.
- Decision controls live in the Control Mirror page; deeper integration into the broader Human Review workspace remains open.
- Actor/rationale validation is present, but richer authorization by mandate role is not yet implemented.
- Source ingestion expansion still needs retention, redaction and source-mode policy before broad repository/log evidence support.
- The Control Mirror domain file is becoming a convergence point for generation, report logic and lifecycle summary behavior.

## Next Epic Preparation

No Epic 3 is currently defined in sprint tracking.

Recommended next paths:

1. Source ingestion expansion: uploaded zip or folder snapshot with retention/redaction and path-safety rules.
2. Evidence parsing expansion: richer parser/normalizer modules with source excerpt policy.
3. Report/export expansion: durable Control Mirror report artifacts and evidence pack export.
4. Human Review workspace integration: show Control Mirror queue and decision history directly in `/review`.

Recommended starting point: define the next epic as **Source Ingestion and Evidence Policy** if the goal is broader real-world evidence coverage, or **Human Review Workspace Integration** if the goal is governance usability.

## Retrospective Outcome

Epic 2 is complete from story, test and build perspectives. The completed foundation is strong enough to support the next product move, but the next move should be deliberately chosen. The biggest technical caution is module size; the biggest product caution is source/evidence policy before ingesting broader material.
