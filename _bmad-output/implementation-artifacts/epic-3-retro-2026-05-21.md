# Epic 3 Retrospective: Source Ingestion and Evidence Policy

Date: 2026-05-21
Project: AAS-Companion
Epic: Source Ingestion and Evidence Policy
Status: completed

## Executive Summary

Epic 3 completed the next trust layer for Control Mirror. The system now distinguishes supported, planned and unsupported source modes; validates uploaded snapshot contents before persistence; applies source retention and redaction policy before storing excerpts; and refreshes uploaded snapshots deterministically by normalized path and hash.

The strongest outcome is that broader source ingestion no longer depends on vague UI copy. It has domain-owned policy, persistence guardrails and tests around the highest-risk behaviors: unsafe paths, unsupported files, secret-like content, partial processing and duplicate refresh noise.

The main remaining product question is how far Control Mirror should now go toward a real user-facing upload/connector workflow. The backend contract is ready for an upload adapter, but folder/repository scanning and Git connectors should remain non-actionable until explicit user authorization and connector semantics exist.

## What Worked

- Starting with a source-mode policy surface kept later ingestion work honest. Unsupported local folder and Git/repository modes are visible but not presented as live scanning.
- Treating uploaded snapshots as already-extracted file lists kept Story 3.2 focused on safety boundaries instead of pulling in zip extraction too early.
- Reusing `ControlMirrorSource`, `ControlMirrorSnapshot`, `ControlMirrorArtifact` and normalized evidence models avoided new schema churn for policy state.
- Redaction and retention are domain/service-owned, not only UI text. That makes report disclosure and persistence behavior line up.
- Deterministic refresh by normalized path and SHA-256 gives uploaded snapshots the same kind of stable comparison semantics that Epic 2 needed for Human Review reconciliation.
- Focused tests caught a real redaction bug: a generic authorization rule initially left part of a bearer token visible. The test forced the rule to redact the full credential shape.

## What Was Hard

- Control Mirror now crosses many layers in every meaningful change: domain read model, DB repository, App Router page and focused Vitest coverage.
- `packages/domain/src/control-mirror.ts` is carrying source policy, retention, conformance, review, report and dashboard logic in one file. It remains coherent, but its review surface is getting heavy.
- TypeScript exact optional property semantics are useful but require discipline when mapping optional JSON metadata out of Prisma.
- JSON metadata in Prisma needs careful typing. Retention metadata fits the existing fields, but lineage JSON now carries more behavioral meaning than before.
- Redaction rules are necessarily conservative. They reduce risk, but they are not a complete secrets scanner and should be described that way in product language.

## Key Lessons

1. Policy before capability is the right sequence for evidence ingestion. It prevented the UI from implying silent local access and kept unsupported modes non-actionable.
2. A narrow backend intake contract is enough to harden the core rules before adding a visible upload surface.
3. Retention metadata should travel with evidence lineage, not only with source-mode copy. Reports need to disclose what was retained, redacted or omitted.
4. Secret redaction tests need concrete credential shapes. Generic regex confidence is not enough.
5. Stable normalized paths and content hashes are the right anchors for uploaded snapshot refresh and later Human Review reconciliation.

## Quality And Readiness Assessment

Testing and quality: Green for targeted Control Mirror coverage and production build.

Deployment readiness: Code builds successfully. No new schema tables were required for Epic 3.

Stakeholder acceptance: Not formally recorded. Product/security review should confirm retention labels, supported source-mode language and redaction disclosure before enabling a visible broad upload workflow.

Technical health: Stable, with one clear refactor pressure point. Control Mirror has enough logic in the domain file that extraction into source policy, retention, conformance and report modules should happen before another large Control Mirror expansion.

Known residual risks:

- There is no visible upload UI for uploaded project snapshots yet; the backend entry point is ready for a future adapter.
- Zip extraction itself is not implemented; path validation assumes the adapter provides an extracted file list.
- Redaction catches common secret-like patterns but is not a full security scanner.
- Retention metadata is stored in JSON lineage rather than dedicated policy columns.
- Folder snapshot and Git/repository root remain planned/unsupported until real explicit authorization or connector flows exist.

## Next Epic Preparation

No Epic 4 is currently defined in sprint tracking.

Recommended next paths:

1. Uploaded Snapshot UX and Adapter: add the visible upload flow, extraction adapter, file size limits and user-facing ingestion result states.
2. Control Mirror Modularization: split source policy, retention, conformance, review and report code into smaller domain modules.
3. Report and Evidence Pack Export: turn Control Mirror report output into durable exportable artifacts with retention disclosure.
4. Human Review Workspace Integration: surface Control Mirror review queue and decision history more directly in `/review`.

Recommended starting point: define Epic 4 as **Uploaded Snapshot UX and Adapter** if the goal is to make the new backend capability usable, or **Control Mirror Modularization** if the goal is to reduce implementation risk before adding more surface area.

## Retrospective Outcome

Epic 3 is complete from story, test and build perspectives. The completed foundation is safe enough to support a visible uploaded snapshot workflow, provided the next epic handles archive extraction, size limits, UI states and explicit user authorization carefully.
