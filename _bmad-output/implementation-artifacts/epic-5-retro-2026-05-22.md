# Epic 5 Retrospective: Control Mirror Modularization

Date: 2026-05-22
Project: AAS-Companion
Epic: Control Mirror Modularization
Status: completed

## Executive Summary

Epic 5 reduced Control Mirror change risk by extracting the highest-churn helper families out of the central dashboard engine. Source policy/upload validation, Human Review state/stable identity and report/retention summary composition now live in focused domain modules with direct regression coverage.

The important outcome is not new product behavior. It is a safer implementation shape for the next capability family. `control-mirror.ts` still assembles the full dashboard, but it no longer owns every supporting rule directly.

## Epic Review

### Completed Stories

- Story 5.1: Extract Source Policy and Uploaded Snapshot Domain Helpers
- Story 5.2: Extract Human Review State and Stable Finding Identity Helpers
- Story 5.3: Extract Report and Retention Summary Composition
- Story 5.4: Add Module-Level Regression Coverage for Control Mirror Boundaries

### Verification Summary

- Runtime package builds passed across all stories.
- Targeted Control Mirror tests passed after each extraction.
- Web production build passed after each extraction.
- New direct module boundary tests cover source/upload, Human Review and report/retention helpers.

Existing non-blocking warnings remain:

- Vitest sandbox runs can fail resolving `vitest.config.ts`; approved reruns outside sandbox pass.
- React test warnings for non-boolean `jsx` and `global` attributes.
- Next ESLint plugin warning.
- Webpack cache snapshot warnings during production build.

## What Worked

- Mechanical extraction worked well because Epic 4 had already clarified the domain responsibilities.
- Keeping public exports routed through `@aas-companion/domain` preserved compatibility while allowing internal files to shrink.
- Moving stable finding identity into the domain layer made DB queue persistence depend on the same canonical rule as future domain tests.
- Direct boundary tests now protect the extracted modules without requiring every check to build a full dashboard fixture.

## What Was Hard

- `control-mirror.ts` remains the central assembly point, so type-only imports had to be handled carefully to avoid runtime cycles.
- The DB package had an existing re-export of `createControlMirrorHumanReviewStableKey`; preserving that compatibility required a repository-level re-export.
- The build/test warnings are still noisy enough that real failures need careful reading.

## Key Lessons

1. Refactor slices are safest when each extracted helper family already has existing integration coverage.
2. Stable identity rules belong closer to domain semantics than persistence plumbing.
3. Public export compatibility is part of the contract; moving code is not complete until package consumers still build.
4. Boundary tests should assert exact stable strings and disclosure text where product trust depends on wording.
